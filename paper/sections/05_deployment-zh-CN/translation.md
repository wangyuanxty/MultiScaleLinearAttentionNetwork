# 5.1 约束与设计目标

我们的目标平台是电池管理系统内部的微控制器，它在无云端链路、无设备端重训练、无应用处理器的条件下运行。该平台施加两条约束：与保护、均衡逻辑并行运行的固件不得动态分配内存；一次预测的代价不得随运维方所取用的历史长度而增长，因为电池在其整个寿命内被持续监测，其历史只会不断累积。本实现直接满足第一条：freestanding 的 C99 代码；一个在超量分配时报错、而非越界覆写其数组的静态池分配器；以及以 const 数组形式驻留 flash 的权重。本工作的重点不是模型在所评估的窗口下比基线更小或更快，而是其状态尺寸不随窗口长度增长：它每层固定为 d_k × d_v，窗口加长只增加激活值暂存区（与 token 数成线性），而二次注意力缓冲随上下文的平方增长，因而加长窗口就不得不扩大缓冲，或对同一段历史采用更粗的表示。

# 5.2 跨架构数值保真度

实现的是完整多尺度模型，而不只是单分支编码器。两个变体共用同一份 GDN-2 内核实现，因此为编码器建立的逐位一致性，无需第二套验证论证，即可延续到第 4 节所报告的模型。

部署声明通常止步于"它能跑"。我们可以做得更好：同一份 C 源码分别编译到宿主机与 Cortex-M3，并在完全相同的输入下比对：

- 宿主机的 C 实现对照 PyTorch 前向：多尺度模型的相对误差为 1.07×10⁻⁶（单分支编码器为 2.5×10⁻⁶）；
- Cortex-M3 二进制文件（QEMU mps2-an385，Arm GNU 工具链 13.2.rel1）对照宿主机二进制文件：多尺度模型为 5.96×10⁻⁸，约为 float32 的半个 ULP（编码器为 1.19×10⁻⁷）。

第二个数字更重要：它意味着部署后的模型不仅平均意义上准确，而且跨指令集可复现——直到递推所依赖的 expf/logf/sqrtf/erff 调用。ARM 软浮点与 x86 的运算结果仅差最低一位。

# 5.5 延迟与能耗

在模拟的 Cortex-M3 上，完整多尺度模型的一次推理耗费 4.88×10⁷ 个 SysTick 节拍。三个输入窗口分别给出 48,755,486、48,756,706 和 48,753,240 个节拍——离散度 0.007%。为带浮点单元（FPU）的内核重新编译后，同一次推理耗费 3.39×10⁶ 个节拍，减少到 1/14.4。本节自始至终同时沿用这两个数字，因为一次部署实际看到的是哪一个，取决于所用芯片而非模型本身——而两者之差，正是下文推导出的两个计时结果的分野所在。

这一数字是一个模拟出来的 SysTick 计数，而在它能说明任何问题之前，必须先锚定该计数器的两个性质。只有采用指令计数计时（instruction-count timing）时，它才跟随客户机而非宿主机推进：在 `-icount shift=0,sleep=off` 下，一条已执行的指令等于一纳秒虚拟时间，这就把 SysTick 的参考频率精确地置于 25 MHz——即 MPS2 开发板自身的 SYSCLK——因此一个节拍等于四十条指令。其次，它是一个 24 位递减计数器，而单次推理的跨度超过其 16.8×10⁶ 个节拍的重载周期，因此在异常处理程序中统计重载次数，并通过顺序锁（seqlock）读取计数值。同一份源码以 `-O0` 构建时报出 57.13×10⁶ 个节拍，而 `-O2` 下为 48.76×10⁶。

换算成指令数，这是 1.95×10⁹ 条，FPU 版本为 1.36×10⁸ 条。指令数是模拟器直接测得的量；要换算成周期数，还需要一个它无法提供的每指令周期数（CPI）。取 CPI≈1.3——该内核上编译后 Thumb-2 代码的代表值——一次推理在软浮点下为 2.54×10⁹ 个周期，带 FPU 时为 1.76×10⁸ 个周期。在模拟器的 25 MHz 下，这分别是 101 s 和 7.1 s；而在 Cortex-M7 部件所运行的 200 MHz 下，FPU 版本为 0.9 s。把每条指令都计以相同虚拟时间的计时方式，无法为 FPU 指令多出的周期定价，而单精度乘除法在真实硅片上各需数个周期，因此 14.4× 的指令数比值高估了实际耗时收益——而那些部件更高的主频又把结果推向另一边。请把 0.9 s 当作估计值，把 7.1 s 当作模拟器本身所能支撑的数字。

这 101 s 是由三项保守选择拼装出来的，而非模型的固有属性。第一项是时钟：25 MHz 是 MPS2 开发板自身的频率，远低于带 FPU 部件的运行频率。第二项是内核。MPS2-AN385 是一颗 Cortex-M3，没有浮点单元，因此每一次 fp32 乘法与加法都变成一次软件例程调用；链接后的二进制文件中含有 225 处指向这些例程的调用点。同一份源码在 Cortex-M7 镜像上以软浮点构建耗费 48.76×10⁶ 个节拍——与 Cortex-M3 的数字相差在 0.02% 以内，因为计数由这些例程主导——所以 FPU 版本的 3.39×10⁶ 是同内核对比测量，仅 FPU 一项就削减了 14.4× 的指令数。它还消除了输入敏感性，从上面三个窗口之间 0.007% 的离散度降至 6×10⁻⁷，因为分支跳转正存在于被 FPU 取代的那些软件例程之中。第三项是内核实现：一个朴素的三重循环矩阵–向量乘法，未做展开。BMS 设计确实在用的 Cortex-M4F 与 M33 部件则带有 FPU。这两种构建并非逐位相同——融合乘加改变了舍入方式，结果在相对意义上相差约 3×10⁻⁶。这与本节前文报告的主机构建与 PyTorch 前向之间的一致性处于同一量级，且大于跨指令集的一致性，这是意料之中的：两种构建融合了不同的运算，因而在不同位置舍入。在本模型所支持决策的尺度上，这并非精度问题。

能量由同一计数导出，且与主频无关：记内核电流为 c（单位 μA/MHz）、供电电压为 V，则 N 个周期的一次推理耗费

**E = cVN × 10⁻¹² J**

与时钟频率无关。提高主频会按比例缩短推理时间，因此它换来的是延迟而非能量。从运营角度看，真正重要的是占空比：电池管理系统每个充放电循环运行一次该推理，间隔数小时。在 c = 300 μA/MHz、V = 3.3 V 下，一次推理在软浮点下耗费 2.5 J，带 FPU 时为 0.17 J；摊到数小时的一个循环上，平均功耗低于一毫瓦——相对于 BMS 自身的静态负载很小，但默认情况下并非可以忽略，而这正是构建占空比预算时应当依据的量。这两个数字都不改变部署论证，因为该论证立足于内存上界而非计时。
